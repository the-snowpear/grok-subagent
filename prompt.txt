==================================================
4. BLOCKER P1-B
MAIN-OWNED FOLLOW-UP SCHEDULING
==================================================

这是本轮最重要的语义修复。

产品契约：

Codex/Main 是唯一 orchestrator。

workers 可以：

- 提供 evidence；
- 提供 findings；
- peer clarification；
- peer evidence request。

但 worker 不能在 Main 未 adjudicate 的情况下：

Reviewer
  -> Implementer
  -> 自动产生一个新的修改型 follow-up turn

否则 Main 的决策 authority 只是 prompt etiquette。

----------------------------------
4.1 不要做全面 RBAC
----------------------------------

不要扩成大型权限系统。

不要：

- 新 token subsystem
- ACL engine
- role hierarchy
- capability server
- message policy DSL
- 大量 message kinds
- 重写 mailbox

本轮只需要一个最小 runtime primitive：

**Main 才能自动唤醒 role-tagged orchestrate worker 的 completed follow-up。**

----------------------------------
4.2 Persist role
----------------------------------

当前 role 只在 create time 解析，这不够。

新增：

agents.role

建议迁移：

ALTER TABLE agents ADD COLUMN role TEXT

legacy rows：

role = NULL

不要给历史普通 agent 强行赋角色。

create_agent/create_agents：

resolved role 写入 agents.role。

role 必须在：

status
result

以及已有 public/catalog/detail surface 中合理暴露。

这样 observer/debug 时能知道：

explore
implement
review
NULL legacy

不要把 role 重新解析。

completed follow-up 使用同一个 agent row，所以自然继承 stored role。

----------------------------------
4.3 Main identity
----------------------------------

使用已有 canonical：

main_peer_id(thread_id)

不要根据：

display name
agent name
"Main" 字符串

猜 sender。

----------------------------------
4.4 Auto-followup authority rule
----------------------------------

修改 canonical completed-worker delivery scheduling path：

maybe_schedule_delivery(...)

或真实等价函数。

规则：

IF target agent.role IS NULL:
    保持当前 legacy Agent Fabric 行为不变。

IF target agent.role IN ('explore','implement','review'):
    只有：
        message.from_peer == main_peer_id(agent.thread_id)
    的 pending messages
    才能被自动 claim 到一个新的 follow-up turn。

来自其他 worker 的消息：

- 不删除；
- 不 mark delivered；
- 不 consumed；
- target_turn_id 保持 NULL；
- 不创建 follow-up；
- 保持 pending。

这是重点：

peer message 不等于丢失。

它只是：

**没有 scheduling authority。**

如果 worker 当时处于 active/running 状态并主动通过 inbox/wait
读取 peer clarification，现有协作能力可以继续存在。

但 completed orchestrate worker 不得被 peer 自动重新激活。

----------------------------------
4.5 为什么对全部 role-tagged workers 生效
----------------------------------

不仅 implement。

对：

explore
implement
review

都使用 Main-owned automatic follow-up scheduling。

这样：

Main
  -> Explorer clarification follow-up

允许。

Main
  -> Implementer Fix Order

允许。

Main
  -> Reviewer re-review request

允许。

Reviewer
  -> Implementer

不能自动创建 turn。

Explorer
  -> Reviewer

不能自动创建 turn。

Implementer
  -> Reviewer

不能自动创建 turn。

这让 Main 真正拥有 workflow phase progression。

----------------------------------
4.6 不要求 message kind redesign
----------------------------------

优先采用：

stored role
+
sender gate

不要因为本轮修复新增一个复杂：

work_order/fix_order/evidence/clarification

message-type state machine。

现有 agent_messages.kind 如果已有用途，保持兼容。

Main 发出的普通 message 已经代表 Main 授权，因此可以唤醒
role-tagged worker。

以后若需要细粒度 authority 再单独设计。

本轮不要 scope creep。
